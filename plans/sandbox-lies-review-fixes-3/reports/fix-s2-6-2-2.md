# Fix 6.2/2: a string tool_use input is not a command

Mutant 6.2/2 in `tests/extract-fixtures.py` `iter_calls`: `else None` became
`else inp`, so a non-dict `input` passes through as the command text. The
string-input case in `tests/extract-fixtures.bats` asserted only that the cut
landed, and its odd line carried `"ls"`, which never matches SPEC, so the
mutant survived.

## The case

`a string tool_use input reads as no command, so its matching call is not taken`

The corpus holds one Bash `tool_use` whose `input` is the JSON string
`"git commit --amend --no-edit"` (id `m1`, 10:00:00), and a `tool_result`
for `m1` carrying the lock refusal text from `lock_text`. The cut is run and
asserted: exit 1, `NOT FOUND: fire-lock-commit-amend` on stderr, and no file
under the scratch `tests/fixtures/`.

State that fails it: the input is a string, which the real code treats as
having no command, so the result is never paired and the cut finds nothing.
What else could produce exit 1 with that message: a corpus the cutter cannot
read at all (the same message would print) and a missing SPEC entry (which
prints `NOT IN SPEC` instead). The `NOT FOUND` substring check and the
`[ ! -e ]` file check distinguish a skipped pairing from those cases only in
part; a corpus-unreadable failure would still pass. The sibling case
`a null timestamp ...` (6.2/1, commit 9b0ef52) and the `matching_call` helper
used by the scalar case are unchanged.

## Verification

- The case builds its corpus at run time under `$BATS_TEST_TMPDIR`; no file
