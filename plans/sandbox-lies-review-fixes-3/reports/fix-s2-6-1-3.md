## Subject

`tests/corpus-eval.py` `cmd_extract`, the `tool_use` input guard:

    cmd = inp.get("command") if isinstance(inp, dict) else None

The guard lets a dict input through and sends every other shape to
`None`, so a non-dict input is skipped and cannot crash the walk.

## Change

`tests/corpus-eval.bats`: one case added after the scalar and array
case, `extract reads a list, number or null tool_use input as no
command`. It writes three `tool_use` Bash lines built at run time with
`corpus_use_raw_input`, with the input `["ls"]`, `42` and `null`, under
the ids `u2`, `u3` and `u4` (`one_call 1` owns `u1`). It then appends a
survivor with `one_call 1` and asserts:

- `extract` exits 0;
- exactly one survivor file exists;
- `survivors/000001.txt` exists.

The file is 120 lines after the edit, under the 400 cap. No fixture
file is added.

## What fails it

The state that fails it: a `tool_use` Bash input that is a JSON list, a
number or `null`, in a session file that also holds a survivor. The
walk must skip those inputs and still extract the survivor.

What else could produce the same red: a traceback from any other
parsing step on those lines would also exit non-zero. The line
`cmd = inp.get(...)` is the only code that touches the input, and the
same file's string case and scalar/array case already cover the
other lines, so a non-zero exit here comes from the input shape.

What else could produce the green: a bare crash-free exit with a
survivor missing. The survivor-count and file-existence asserts rule
that out.
