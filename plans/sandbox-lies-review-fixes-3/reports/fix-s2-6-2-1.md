# Fix 6.2/1 — a null timestamp's call is observed

Finding 27 (`plans/sandbox-lies-review-fixes-3/reports/deliverable-review.md`),
mutant 6.2/1 in `reports/deliverable-review-code-tests-phases2-6.md`: `iter_calls`
reads a null timestamp as the fixed day `2026-08-13` (`or "2026-08-13"` in place
of `or ""`).

## Subject behaviour

`tests/extract-fixtures.py` `iter_calls` computes `day` per JSONL line as
`(e.get("timestamp") or "")[:10]`. A null timestamp therefore reads as no day
(`""`). `pick` skips a call whose day is set and differs from the entry's day
(`if day and d != day`), so a dated SPEC entry never takes a call whose result
line has no timestamp. The day is taken from the tool_result line, which is the
line that yields the output.

## Test change

`tests/extract-fixtures.bats`, case "a null timestamp reads as no day, so a
dated entry does not take its call" (replaces "a null timestamp reads as no day
and the cut still lands"):

- The odd line is now the matching call's tool_result, with `timestamp: null`
  (paired with a dated tool_use, as a real transcript would carry it). Built at
  run time with `jq` and `lock_text`, no fixture file.
- Asserts the cut does not land: `status` 1, `NOT FOUND: fire-lock-commit-amend`
  in the output, and no `tests/fixtures/fire-lock-commit-amend.txt` in the
  scratch tree.

The old case put a null timestamp on a text-only line that carried no call, so
the day never reached `pick` and the mutant was unobserved. The cut-lands
behaviour from a dated call remains covered by the other cases, which use
`matching_call` with a dated result line.

## What fails the case

- The call's result line has a null timestamp and the entry pins a day: the
  correct code skips it and the cut fails. Any code that gives a null timestamp
  a real day (the mutant, or a default taken from the file, the process clock or
  the tool_use line) cuts the call and fails the status assertion.
- Other causes that would produce status 1 with the same message: a missing
  corpus directory or a bad project name. The dated cases in the same suite
  (`assert_cut_verbatim`) rule out a broken cutter, since they cut the same call
  from a dated line and pass.

## Mutation proof

Mutation: in `tests/extract-fixtures.py`, the once-occurring string
`day = (e.get("timestamp") or "")[:10]` replaced by
`day = (e.get("timestamp") or "2026-08-13")[:10]`.

1. Mutation landed: `command grep -c '"2026-08-13")\[:10\]' tests/extract-fixtures.py`
   prints `1`.
2. Suite under the mutant (`scripts/run-bats.sh tests/extract-fixtures.bats`):

   ```
   not ok 1 a null timestamp reads as no day, so a dated entry does not take its call
   # (in test file tests/extract-fixtures.bats, line 51)
   #   `[ "$status" -eq 1 ]' failed
   bats: 3 passed, 1 failed
   ```

   Red on the case's own status assertion; the cut landed under the mutant.
3. Restore by the swapped replacement (`"2026-08-13"` back to `""`), not from a
   backup. `command grep -c '"2026-08-13")\[:10\]' tests/extract-fixtures.py`
   prints `0`; `git diff --quiet -- tests/extract-fixtures.py` exits 0.
4. Suite after restore: `bats: 4 passed, 0 failed`.

Before the test change the suite was green on unchanged code (4 passed). The
mutant was surviving because the old case never gave the null timestamp a call
to attach to.
