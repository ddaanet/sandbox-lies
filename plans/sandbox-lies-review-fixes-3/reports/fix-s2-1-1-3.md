# Fix S2 — pin 1.1/3: readonly newline path prints its path= line

Source: `reports/deliverable-review.md` (mutation row 1.1/3, SURVIVED) and
`reports/deliverable-review-code-tests-phase1.md`, finding 3.

## Change

`tests/probes-readonly-members.bats` gains one case, placed after the
newline case in the "resolved refused path" section:

"a resolved refused path holding a newline under a read-only directory gives
readonly and one encoded path= line"

The case creates a directory whose name holds a newline (`r<LF>readfile=x`),
sets it to mode 555, and probes the refused relative path `a` with that
directory as cwd. It asserts the whole output: `readonly`, then one
`path=$'<tmp>/r\nreadfile=x/a'` line. It skips when run as root, since root
writes through a 555 directory. The mode is restored straight after the probe.

No library file changed.

## What fails the test, and what else could produce the output

- Failing state: `probe_readonly_path` prints `readonly` but no `path=` line
  for a newline-bearing path. Also failing: a path= line in any other form
  (raw newline splitting the line, a backslash form, or a different path).
- Other producers of the same output: a `writable` outcome (blocked by the
  555 mode for the suite's uid, and checked by the existing writable case),
  or a path resolved against the wrong base (the case uses a relative
  operand, so a wrong join changes the printed path).
- Residual: the case proves the outcome and the path line together; it does
  not separately prove the facts block stays withheld under readonly. The
  existing writable cases cover the facts block.
